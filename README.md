# gagiknavasardyan.github.io

Personal site — a single-page portfolio plus a static blog. Hand-built HTML, CSS and
vanilla JS; the blog is generated by a small Python script. No frameworks, no npm.

```
index.html          the portfolio (hand-edited)
styles.css          design tokens + portfolio styles
script.js           portfolio behaviour

theme.js            light/dark toggle — loaded in <head> on every page

build.py            the blog builder
posts/              blog sources — you write these
templates/          page templates the builder fills in
blog.css / blog.js  blog-only styles and behaviour

writing/            GENERATED — do not hand-edit
assets/posts/       images used by posts
assets/covers/      drop an image here to set a post's index picture
```

## Adding a post

### 1. Create the file

In `posts/`, named `YYYY-MM-DD-slug.md`:

```
posts/2026-09-04-latent-dynamics.md
```

The date prefix is stripped to form the URL, so that file publishes at
`/writing/latent-dynamics/`.

### 2. Write it

```markdown
---
title: Latent dynamics, honestly
date: 2026-09-04
tags: [world-models, rssm]
summary: One line for the index card and the link preview.
---

Your opening paragraph. If you leave `summary` out, this gets used instead
(truncated to ~180 characters).

## A section

Inline math like $z_{t+1} = f(z_t, a_t)$, and fenced code with a language.
```

Front matter fields:

| Field | Required | Notes |
| --- | --- | --- |
| `title` | yes | Used as the h1, page title, and OG title |
| `date` | yes | `YYYY-MM-DD`. When you wrote it. The build fails loudly if this is missing or malformed |
| `paper` | no | `YYYY-MM-DD` — the release date of the paper the post is about. See below |
| `tags` | no | `[a, b]` — becomes the coloured labels and feeds the filter bar |
| `summary` | no | Falls back to the first paragraph |
| `image` | no | Index picture, as a path relative to the site root. Overrides `assets/covers/<slug>.*` — see below |
| `slug` | no | Overrides the URL, which otherwise comes from the filename |
| `draft` | no | `true` keeps it out of the site entirely — see below |

### Paper dates

For posts about a specific paper, set `paper` to the paper's release date. That date is
what the index card and the post header show — rendered as `paper · Jan 19, 2023` — and
it is what the index sorts on, so the blog reads as a timeline of the literature rather
than of the writing.

`date` still means when *you* wrote the post. Omit `paper` and everything falls back
to `date`.

### Live posts

Add `live: true` to the front matter of a post you keep updating — a reading list, a
history that grows with new papers. It gets a pulsing **LIVE** badge in the top-right
corner of the page and of its card on the index; hovering it fills it red and shows a
short note. An "Updated" date appears before the reading time.

That date is `updated: 2026-10-05` from the front matter if you set it, otherwise the day
the markdown file was last saved.

### Index pictures

Each post gets a small square image beside it on the index. To set one, drop a file
into `assets/covers/` named after the post's slug:

```
posts/2026-05-18-path-towards-autonomous-machine-intelligence.md
  ->  assets/covers/path-towards-autonomous-machine-intelligence.png
```

`.png`, `.jpg`, `.jpeg`, `.webp`, `.avif`, `.gif` and `.svg` are all accepted, in that
order of preference if a slug has more than one. No front matter needed — rebuild and
it appears. The card renders it in a 76×76 box (56×56 on phones) cropped to fill from
the centre, so square images work best; ~300×300 is plenty.

Where the builder looks, in order:

1. an `image:` path in the post's front matter
2. `assets/covers/<slug>.<ext>`
3. `assets/posts/<slug>/thumb.svg` — the small line drawing shipped with each post

Those fallback drawings are designed for the same box: `viewBox="0 0 96 96"`,
transparent background (the card supplies the frame and rounded corners), and the
site's greens — `#10855C`, `#0A6B49`, `#86D8AE`, `#3F8F86`. A post with none of the
three simply renders without a picture.

### 3. Preview it

```bash
python3 build.py --serve
```

Rebuilds everything and opens `localhost:8000`, then **watches for changes**: save a
post, a template, a stylesheet, `blog.js` or anything in `assets/`, and the site
rebuilds and the open tab reloads itself. No need to restart it.

The reload script is injected into the dev server's *responses* only — it is never
written to `writing/`, so what you commit is unaffected. A post with broken front
matter prints the error and leaves the server up; fix it and save again.

`--serve` also passes `--drafts` through, so `python3 build.py --serve --drafts`
keeps rebuilding drafts too.

Use `--serve` rather than double-clicking `index.html`. Clean URLs like `/writing/`
only resolve to `index.html` over HTTP; opening files directly gives you a folder
listing. (There is a `file://` fallback in the JS so double-clicking mostly works,
but `--serve` is what the live site actually does.)

## Build commands

```bash
python3 build.py                  # build published posts
python3 build.py --serve          # build, then preview on localhost:8000
python3 build.py --serve --port 8001
python3 build.py --drafts         # include drafts, for local preview only
python3 build.py --clean          # wipe writing/ and rebuild from scratch
```

Output is `writing/index.html` plus one `writing/<slug>/index.html` per post.

`writing/` is reconciled on every build: a post you delete or flip to `draft: true`
has its page removed, so it stops being reachable at its old URL.

## Markdown reference

Supported: `##`/`###` headings (with hover anchors), paragraphs, `**bold**`,
`*italic*`, `` `inline code` ``, `[links](url)` (external ones open in a new tab),
bullet and numbered lists, `>` blockquotes, `---` rules, pipe tables, fenced code
blocks with a language, `$inline math$`, `$$display math$$`, images, and raw HTML.

**`_underscores_` do not produce italics.** They collide with LaTeX subscripts and
Python identifiers, which appear constantly in this kind of writing. Use asterisks.

**Code** is highlighted at build time by Pygments — nothing ships to the reader.
Specify the language on the fence:

    ```python
    model = RSSM(latent_dim=32)
    ```

**Math** uses KaTeX, loaded from a CDN and only injected on posts that actually
contain math. Display equations scroll horizontally on narrow screens.

**Name every symbol.** Each display formula is followed by a line of prose naming what
each symbol stands for, and an inline symbol is introduced the first time it appears. No
symbol tables, no collapsibles: one sentence, in the same voice as the rest of the post.

**Images** go in `assets/posts/<slug>/`, referenced from the post as:

```markdown
![Rollout drift](../../assets/posts/latent-dynamics/drift.png "Optional caption")
```

An image alone on a line becomes a `<figure>`, with the quoted part as the caption.
Do **not** put images inside `writing/` — that directory is generated, and `--clean`
deletes it.

**Raw HTML**: any block starting with `<` passes through untouched. This is the
escape hatch for inline SVG diagrams, embedded video, or interactive demos. It is also
how the figures in the post bodies are written — a `<figure>` with an `<img>` and a
`<figcaption>`, so the caption can carry a link.

### Collapsible asides — `cfyb`

For a clause the reader is welcome to skip — a definition, a mouthful of jargon, an
aside — wrap it in braces and tag it:

```markdown
**Area 6** is {the premotor and supplementary motor cortex}{cfyb} handling motor planning.
```

It renders as a small `cfyb` pill ("closed for your best") that expands on click and
collapses again. `cfyb` must follow the closing brace immediately, with no space. The
aside can contain any other inline markup, but not nested braces.

The builder emits the text **visible** and `blog.js` hides it on load, so with
JavaScript off the sentence simply reads in full. If you ever drop `blog.js` from a
page, the asides stay open rather than vanishing.

Hovering the pill shows an instant tooltip. Any element with the `has-tip` class and a
`data-tip` attribute gets the same one.

### Optional sections — block `cfyb`

For a whole passage the reader can skip — a joke, a digression — put `{` on its own
line before it and `}{cfyb: Button label}` on its own line after it:

```markdown
{

Did you notice the **9** under the World Model?

| Answer | $p$ |
| --- | --- |
| Yes | 0.0001 |

}{cfyb: Did you notice?}
```

It renders as a large full-width button with the label and an "optional" badge; a
click opens the passage in a panel underneath. Everything inside is ordinary markdown —
paragraphs, figures, tables, math, code, inline `cfyb` pills. Leave out the label
(`}{cfyb}`) and the button reads "closed for your best". Both lines must stand alone,
with blank lines around them. An unclosed `{` fails the build. As with the inline
form, the passage ships visible and `blog.js` folds it away.

### Expandable rows — `cfyb row`

For several of these in a stack — the parts of an architecture, the steps of a method —
add `row` before the label:

```markdown
{

It reads the senses and estimates the current state of the world.

}{cfyb row: Perception — estimates the current state of the world}
```

Same behaviour, quieter shape: a bordered row instead of a banner, no "optional" badge.
The label is split on the em dash, so `Name — summary` renders the name in the site's
green and the summary in muted text beside it (below it on narrow screens). A label with
no dash is simply the name. Rows sit close together, so a run of them reads as one list.

### Expandable cards — `cfyb card`

The same row, drawn larger — a filled chevron, bigger type, a tinted button. Use it for
core content the reader should open, like a lemma or a theorem, rather than an aside:

```markdown
{

Whenever $\lambda_K > \lambda_1$, there exists a downstream task for which …

}{cfyb card: Lemma 1 — anisotropy amplifies bias}
```

### Paper buttons — `cfyb paper`

For long lists of papers, like the world-model map. The name and the summary sit on two
separate lines, so every button in the list is exactly the same height:

```markdown
{

Short description of the paper.

[Paper](https://arxiv.org/abs/...) · [My post](../slug/)

}{cfyb paper: DreamerV3 (2023) — one configuration across 150+ tasks}
```

Write `cfyb paper post:` instead to add a green **My post** mark on the right of the
button, for papers you have written about.

**Body text is justified** with automatic hyphenation, falling back to ragged-right
below 620px where the measure is too narrow for it to look good.

### Reusing figures from papers

Figures in the posts come from the papers themselves where the licence allows it. Check
before adding one — the licence is at the bottom of the arXiv abstract page:

| Licence | Can you republish the figures? |
| --- | --- |
| CC BY 4.0 | Yes, with attribution |
| CC BY-SA 4.0 | Yes, with attribution; adaptations must stay CC BY-SA |
| arXiv non-exclusive | **No** — draw your own diagram instead |

Captions credit the source in the form: *Figure from [Paper Title](link) (Authors,
Year), [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/).* Figures drawn from
scratch say so, to keep the distinction visible.

A full worked example lives in `posts/2026-08-27-formatting-reference.md`. It is a
draft, so run `python3 build.py --drafts` and open "How this blog is built" to read
it rendered.

## Two navs

The portfolio (`index.html`) keeps the full section menu and the mobile hamburger. The
blog templates carry **only** the Blog pill — the `GN` logo is the way back. With one
item there is nothing to collapse, so the hamburger is removed from those templates
entirely and `.blog .nav-menu` stays a visible row at every width.

`blog.js` guards its nav code with `if (toggle && menu)`, so the missing hamburger is a
no-op rather than an error. If you ever add links back to the blog nav, restore the
`.nav-toggle` button too, or they will be unreachable on a phone.

**Where you are:**

| | `GN` logo | Blog pill |
| --- | --- | --- |
| Portfolio | green lettering, box unchanged (`.nav-logo.active`) | outlined, green-tinted |
| Blog | plain | solid accent (`.nav-writing.active`) |

`.active` on the logo is set by hand in `index.html`; the blog templates leave it off.
It only changes `color`, and is declared before `.nav-logo:hover` so hovering still
reads normally on top of it.

## Light and dark

The button at the far right of the nav toggles the theme. It sits in `.nav-actions`,
deliberately outside the `<ul>` of links, so it reads as a control rather than a nav
item — and on the portfolio it stays grouped with the mobile hamburger, which
`space-between` would otherwise fling to the other end of the bar. Preference order is:
an explicit
choice you clicked > your OS setting. Nothing is written to `localStorage` until the
button is used, so following the OS stays the default and keeps working if it changes.

`theme.js` is loaded in `<head>` **without `defer`** on purpose — it has to set
`data-theme` on `<html>` before the first paint, or every navigation flashes white.

Everything else is design tokens. `:root` in `styles.css` holds the light palette and
`:root[data-theme="dark"]` overrides it; `blog.css` adds dark variants for the five
label colours and the syntax-highlighting colours. **If you add a colour, add it as a
token** rather than inline, or it will be wrong in one of the two themes.

Two things cannot follow the tokens and are handled separately:

- **Paper figures** are opaque white PNGs. In dark mode they are dimmed slightly so they
  do not glare, and restored to full brightness on hover.
- **Post thumbnails** load through `<img>`, so page variables cannot reach inside them.
  They get a brightness lift in dark mode instead. Inline SVG in a post body *does*
  inherit variables, so use `fill="var(--accent)"` and friends when drawing diagrams —
  the two existing ones do.

## Labels

Labels are just `tags` — there is no list to register them in. A new tag appears in
the filter bar automatically with a post count, and gets a colour from five muted
slots dealt round-robin over the sorted tag set.

Because they are dealt in order rather than hashed, adding a new tag can shift the
colours of existing ones. That is the tradeoff for guaranteeing two labels sitting
side by side never look identical.

## Drafts

`draft: true` means the post is **not built at all** on a normal run — the page does
not exist, and it is absent from the index.

`--drafts` builds them so you can preview locally. A plain `python3 build.py`
afterwards removes them again.

> **Before pushing, always run `python3 build.py` without `--drafts`.** Otherwise a
> draft you previewed ships as a live, unlinked URL.

## Publishing

GitHub Pages serves these files directly and does not run the build. So commit the
markdown **and** the generated output:

```bash
python3 build.py          # no --drafts
git add posts/ writing/ assets/
git commit -m "post: latent dynamics"
git push
```

## Site configuration

The blog's name, description, author and URL live at the top of `build.py`:

```python
SITE_URL = "https://gagiknavasardyan.github.io"
AUTHOR = "Gagik Navasardyan"
BLOG_TITLE = "Blog"
BLOG_DESCRIPTION = "My notes and essays on machine learning research."
WORDS_PER_MINUTE = 220
```

Changing any of these and rebuilding updates the page and the meta tags together.

The portfolio page (`index.html`) is hand-edited — the builder never touches it.
